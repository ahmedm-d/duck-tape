## Reproduced findings

1. **P1: approve-first intake approves no concrete plan.** `backend/main.py:create_job`, `backend/workflow.py:transition(approve)`, `backend/worker.py:process_job`. API intake immediately creates `Awaiting approval` with no generated plan. Approving stores `plan_hash=None` and `preparation_approved=True`; the worker then generates the first plan and implements it without returning for plan approval. `test_api_approve_first_requires_review_of_generated_plan` observed `Ready for review` instead of `Awaiting approval`. The smallest complete fix is to investigate/plan before the preparation gate, require approval of a concrete current plan, and compare the approved plan hash before implementation. Owner: root/model engine; fix pending independent recheck.

2. **P2: three overlapping policies produce a decision with no options.** `backend/worker.py:constraints`, `backend/knowledge.py:conflicts`. Three policies for the same key (`integer`, `float`, `decimal`) produce pairwise conflicts. Choosing the first policy twice removes both alternatives from `relevant`; the remaining pair still creates a card with `options=[]`. The job cannot leave `Needs input`. `test_three_conflicting_policies_leave_selectable_decision` fails on the empty card. Skip conflicts whose alternatives were already eliminated, or resolve the entire conflicting set once. Owner: model engine; fix pending independent recheck.

3. **P2: changed applicable policy leaves an obsolete preparation plan approvable.** `backend/knowledge.py:ACTIVE/_invalidate`. `Awaiting approval` is absent from invalidation. After the worker pauses on a generated plan, adding an approved `app.py` rule leaves that plan in `Awaiting approval`; approval can then authorize a newly generated approach through the existing boolean. `test_changed_policy_invalidates_waiting_preparation_approval` reproduces the unchanged state. Invalidate the waiting plan and its preparation approval when applicable policy changes; the exact-plan check in finding 1 must also guard resume. Owner: root; fix pending independent recheck.

4. **P2, fixed in this review: summary cache ignores the model selected for summaries.** `backend/summaries.py:build`. With health reporting `main-model`, a summary generated by `STEWARD_SMALL_MODEL=summary-a` remains cached after setting `summary-b`, and the record attributes the summary to the main model. `test_summary_cache_changes_with_actual_summary_model` initially observed no new calls. The cache key now includes the small-model configuration and summary-role capabilities/schema; persisted attribution uses provider telemetry. Existing summary tests and the new regression passed: **4 passed**. This is a two-line production fix; no new abstraction or dependency.

5. **P2: supported planning context requests terminate the job.** `backend/worker.py:process_job` planning branch. The planning schema and prompt permit/encourage `request_context`, but a valid first response is immediately converted into `Failed`. `test_planning_context_request_retrieves_more_evidence` uses a deterministic first planning response asking for `app.py value`, then a valid plan, and confirms the second response is never requested. Handle the request with the same bounded additional-evidence budget used for implementation, then persist the expanded context and updated plan. Owner: model engine; fix pending independent recheck.

6. **P2: persisted stages reuse outputs after the configured model changes.** `backend/worker.py:call`. The stage fingerprint contains request/workflow/label but omits provider endpoint, selected model, prompt and schema identity. A plan paused under `STEWARD_PLANNING_MODEL=planner-a` is replayed after switching to `planner-b`; only implementation/review calls occur on resume. `test_resumed_stages_invalidate_changed_provider_model` reproduces this. Include the actual provider/model/prompt/schema inputs in durable stage identity, as the lower-level provider cache already does. Owner: model engine; fix pending independent recheck.

7. **P2: a destructured TypeScript parameter creates a false resolved caller edge.** `backend/symbols.py:parse_js`. Given `import { value } from './helper'; function run({ value }: { value: () => number }) { return value(); }`, the local parameter call is recorded as a `parsed/resolved binding` to the imported helper. An actual imported `value()` call on the next line supplies the control case. `test_ts_destructured_parameter_does_not_resolve_to_import` observes both edges, when only the final call resolves. Collect bindings from destructured parameter patterns, or leave those calls unresolved. Owner not yet assigned; fix pending independent recheck.
